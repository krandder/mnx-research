Market-maker infrastructure

The journal mirror crossed a line.

A debugging copy of the exchange journal became part of the live market-maker data path. A testnet migration then rebuilt that huge copy, overwhelmed PostgreSQL, and briefly starved the exchange's writer heartbeat.

Promotion blocked Do not ship the current mirror-backed flow design to production.

First move market-maker flow into a small, purpose-built projection and remove every correctness dependency on the raw mirror.

The 30-second brief

Three things matter.

1

No primary journal data was lost.

The destructive work affected a derived PostgreSQL copy. The authoritative JetStream journal and the normal read model remained intact.

2

The architecture is still wrong.

The market maker can become wrong or unavailable when an optional forensic mirror is stale. Debug infrastructure must not control trading.

3

The replacement is small.

Keep the same flow API, but back it with a tiny table written by the authoritative materializer. No exchange rewrite is required.

Plain-English vocabulary

What each piece actually does.

The names sound similar, but these components have very different jobs.

J

Authoritative journal

The ordered record of what the exchange did. It lives in JetStream and is the source from which state can be rebuilt.

Think: the bank's legal ledger.
M

Materializer

The trusted worker that reads the journal in order and updates useful PostgreSQL tables such as balances, orders, and positions.

Think: the clerk producing account statements.
R

Raw journal mirror

A large searchable PostgreSQL copy of raw envelopes and facts. It helps humans investigate incidents. It may be stale or off.

Think: security-camera footage.
F

Flow projection

A small table containing only the child-vault lifecycle events needed by the market maker, with an exact cursor.

Think: a purpose-built transaction feed.

What happened on testnet

A debugging rebuild became an exchange incident.

The reader shutdown was an authenticated operator action. The dangerous part was what the mirror did automatically when it restarted.

12:37 UTC Reader stopped

The testnet reader group was explicitly scaled from one to zero.

Migration 232 Cursor marked unknown

The old mirror cursor was deliberately labeled as unbound.

12:45 UTC Reader restarted

The mirror saw a generation mismatch and chose a full rebuild.

125M rows Huge deletion

About 90M exchange and 35M relayer envelopes were deleted.

78 connections PostgreSQL saturated

Up to 59 sessions waited on write-ahead-log contention.

7–10 seconds Writer fenced itself

The lease confirmation became stale, so side effects stopped safely.

What was harmed

Database capacity, writer-heartbeat reliability, oracle-update continuity, and confidence in the production rollout.

What remained safe

JetStream history, the authoritative materialized state, user balances, and the normal exchange read model.

The architectural mistake

The market maker depends on the wrong table.

PR #506 made the child-vault flow endpoint query the raw forensic mirror. That turned an optional debugging tool into a production correctness and availability dependency.

Current path

Unsafe boundary
JetStream journal authoritative
→
Raw journal mirror optional, huge, can lag for days
→
Flow endpoint waits for mirror catch-up
→
Market maker quotes or stops

If the debugging mirror falls behind, the market maker either reads an unsafe cursor or receives 503 and stops quoting. Both outcomes prove the dependency is in the wrong place.

Why generation IDs exist

A safety label—not permission to reset.

Journal sequence numbers start again at one if a stream is ever recreated. A generation ID prevents an old cursor from silently being used against a different stream.

Old stream

Generation G1
Cursor: 91,000,000

Valid only for the first journal incarnation.

≠

New stream

Generation G2
Cursor: 1

A new sequence space that must never inherit the old cursor.

Correct rule: store the active generation on the projection's small high-water record. If it changes, fail closed and require an explicit reviewed recovery. Never automatically delete millions of rows.

The production-safe replacement

Let the trusted materializer write one small feed.

The flow endpoint can keep the same contract. Only its backing store changes—from raw forensic facts to a purpose-built projection.

Desired path

Production-safe
JetStream journal authoritative
→
Materializer ordered, transactional
→
Child-vault flow projection small, indexed, exact cursor
→
Market maker same flow API

The raw mirror remains available for operator investigation, but nothing user-facing or trading-critical depends on it being enabled, complete, current, or retained.

Decisions to lock down

The operating policy should be unambiguous.

Production journal Never reset routinely. A generation change is an explicit disaster-recovery event.
Testnet journal No automatic resets. Any destructive reset is deliberate, stopped, reviewed, and operator-run.
Raw mirror Optional forensics only. It may be disabled, stale, incomplete, or retained without affecting trading.
Generation mismatch Fail closed; never auto-delete. Preserve evidence and require explicit recovery.
Market-maker flow Purpose-built projection. Small schema, exact cursor, transactional materializer writes.
Production promotion Blocked until the flow endpoint no longer reads the raw mirror.

Before prod

CEO questions

The short answers.

Did we lose trades or balances?

No evidence of that. The deleted data was a derived forensic copy, not the authoritative journal.

Why did the exchange react at all?

The huge PostgreSQL delete and replay competed with the writer's lease heartbeat for the same database resources.

Why keep generation IDs?

They prevent accidental mixing of two journal incarnations. They are a cheap safety fence, not a reset mechanism.

Does #516 solve production readiness?

No. It prevents corrupt flow by returning 503, but the raw mirror can still take the MM offline.

Do we need a large new service?

No. One small projection written by the existing materializer is enough.

When can this go to production?

After the flow endpoint is independent of the raw mirror and generation mismatch can no longer trigger bulk deletion.
